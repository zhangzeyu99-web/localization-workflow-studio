# 既有术语补全、审核与获批应用

## 适用边界

用户提供已有术语表和语言表，要求补全、优化审核或应用部分建议时执行。本文是 Codex 执行规范，不代表 CLI 已实现自动语义裁决或自动审批写回。术语提取、公告 lookup 继续使用原有脚本；工作台产品和远端表格写回不在本流程授权范围内。

## 1. 区分补空和修改

- 先本地解析真实文件，记录输入、目标语言、已有值和行序。模型只看候选与少量句内证据。
- 术语表独立维护 ID，保留既有 ID 和顺序；来源 ID 仅作追溯。按中文、概念、用途核对，不能因 ID 不同就漏掉可靠补全，也不能仅因 ID 相同就覆盖。
- 空白格有同概念、同用途的可靠译文来源时才补；来源冲突列待核。用户要求不翻译时，没有可靠来源就留空。
- 非空格与语言表不同，只能形成差异候选，不自动认定错误或覆盖。新抽取术语的来源优先级不能代替既有词条修改审批。
- 新增术语按中文去重后追加；不擅自删除历史重复项、重排原表或把主译扩为多个备选。

## 2. 三个决策点

| 问题 | 足够的依据 | 不足时怎么处理 |
| --- | --- | --- |
| 旧译具体有什么问题？ | 错义、漏义、语法错误、正式名称冲突，或可说明的阅读收益 | 只有来源不同、大小写或正常词形差异，通常保留 |
| 新译解决问题且不丢信息吗？ | 保留对象、条件、范围与名称身份；句内词形自然 | 新译收窄含义、改变动作/状态、无依据改名，否决替换 |
| 证据能支持实际使用吗？ | 中文原意、相关句子、人工确认历史、当前用途互相支持 | 缺机制、用途或正式名称证据，列待核，不猜 |

语言表、竞品译法、检索命中、多个模型意见一致，都不能单独证明建议更好或已上线。分类为“动作”也不能证明它实际用于按钮。专名需联查本体、碎片和说明；来源内部不一致时不能挑一个版本当权威。

结论按语言单元格判定，再按词条汇总：

- **保留**：本次替换不采用，不代表已证明原译在所有场景都正确。
- **建议修改**：写清明确修复或可选优化；条件性收益必须带条件，不包装成必改错误。
- **待核**：明确缺少什么游戏事实及具体中文问题，不把外语判断留给用户。

例如：大小写差异可保留；“物理”改成“物理学”应否决；射程与伤害面积需先确认机制；修复通用次数提示的语法，不应顺便限定为“尝试次数”。

## 3. 让用户能够审核

每项调整写清：原译的中文意思、建议译的中文意思、具体问题或收益、证据位置、连带影响和应用条件。禁止只批量填写“与语言表不同，需结合语境审核”。AI 新拟建议明确标为非语言表原译。

审核交付默认只保留“建议修改”和“待确认事项”。保留项、被否决的来源差异及完整证据留在项目 `_work`，不重复塞入干净审核表。保留原译与来源译文的追溯记录，来源译文不得继续标作已认可的建议。

每项建议须能按词条和语言稳定定位。用户用“2、3条”等序号批准时，以其看到的审核表版本映射到术语 ID、CN、语言及旧值；“23条”与“第2、3条”有歧义时先澄清。不能把部分批准扩大为整行、全部语言或所有待核项。

## 4. 获批后应用与正文联查

1. 固定批准清单：术语 ID、CN、语言、旧值、新值。写入前重新读取，旧值已变时停止该项并报告冲突。
2. 只修改获批单元格。未批准的建议、待核项、空白和其他语言保留。
3. 用户同时要求修改正文时，本地检索获批术语相关文本，再按句内意义审核；不做全表机械替换。正文已经一致就不改，具体对象与自然词形保留，缺译不因本次批准而自动补译。
4. 完整术语表保留原结构、ID、顺序与辅助页。用户要求修改清单时，用 `ID / CN / EN / 其他语言`，只列实际修改行，仅本次变化的单元格标黄；术语和语言表的 ID 不混用，必要时分“术语修改”和“原文修改”两页。
5. 遵循用户命名；无其他要求时使用 `名称_YYYYMMDD.xlsx`。原文件不覆盖，过程及校验记录留项目 `_work`。

## 5. 交付前检查

- 所有建议和待核项二次回看：问题、证据、收益与损失是否说清；把语义收窄或证据不足的建议撤回/转待核。
- 从成品读回比对：批准清单与实际差异逐格一致，非目标值和行序不变，修改行不漏不重，黄色单元格对应实际变化。
- 核对占位符、标签、数字、换行、目标文本残留中文与乱码；只扫描实际变更及关联范围，不冒充全量正文深校。
- 分开报告：提出建议、批准、应用、正文一致性、界面验证。没有正文或界面输入时写未执行，不能用文件可读代替语义或界面验收。
- 最终简报给路径、修改条数/格数、校验结果与具体剩余风险。未同步远端时，不声称已经上线或回填。

本规范的结构检查可以脚本化，但中文理由和语义裁决仍需执行者审核；不得声称上述门禁已经全部由通用 CLI 自动强制执行。
