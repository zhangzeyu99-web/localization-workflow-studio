# 验证集与自我沉淀进化最小实现计划

## 结论

先不碰 API、不做复杂自动优化、不引入新平台。最小可行方案是：

1. 先建立固定验证集，防止每次修一个流程又弄坏另一个流程。
2. 再建立失败沉淀库，把真实用户问题转成可复现样本和修复建议。
3. 最后做“人工确认的自我进化”：系统只生成建议，不自动改正式规则、不自动改代码。

这套方案的目标不是炫技，而是让工作台每次迭代都更稳、更少返工。

## 优先级总览

| 优先级 | 目标 | 最小产物 | 不做什么 |
|---|---|---|---|
| P0 | 防回退 | 固定验证集 | 不做 AI 自动分析，不做新 UI |
| P1 | 沉淀问题 | 失败轨迹库 + 问题模板 | 不接复杂日志平台 |
| P2 | 自我进化 | 改进建议队列 + 人工采纳机制 | 不自动改代码，不自动覆盖 prompt/harness |
| P3 | 扩展质量门禁 | 暂不执行 | 不做多租户、不做权限系统 |

## P0：固定验证集

### 目标

把“真实用户会跑的核心流程”变成稳定样本。以后每次改代码，先跑这些样本，避免功能表面可用但流程断掉。

### 最小实现

新增目录：

```text
docs/optimization/validation_set/
  cases/
    001_new_translation_empty_en.md
    002_translation_existing_qa.md
    003_glossary_candidate_from_language_table.md
    004_archive_import_multilingual.md
    005_quick_task_translate.md
    006_announcement_txt_delivery.md
    007_hard_block_recovery.md
    008_cloud_deployment_smoke.md
  README.md
```

每个 case 只写 6 个字段：

```text
任务目标：用户要完成什么
输入文件：用哪个样本文件
操作路径：用户点击顺序
通过标准：什么结果算成功
失败信号：哪些现象算失败
清理方式：测试后如何删除项目/文件
```

### 首批必须覆盖的 8 个样本

1. 新翻译任务：上传空译文语言表，跑翻译、QA、交付。
2. 已有译文校对：跳过模型翻译，直接 QA 到交付。
3. 完整语言表术语候选：完整语言表不能直接进术语库，只能生成候选。
4. 译文归档导入：多语言表导入后，概览页能看到归档，能导出 XLSX/CSV。
5. 快速任务翻译：三步启动，完成后可查看和下载结果。
6. 公告 TXT：上传公告、选择约束、提取术语、反查、翻译、QA、交付。
7. hard block：QA 失败后不能卡死，必须能看到问题、下载问题交付、修复后重新交付。
8. 线上 smoke：`/api/version`、`/api/health`、上传、下载、删除测试项目都正常。

### 验收

- 每个样本都能人工照着跑。
- 每个样本都有明确“成功/失败”标准。
- 后续再写自动化脚本时，不需要重新讨论流程。

## P1：失败轨迹库

### 目标

把用户真实遇到的问题沉淀下来，不再靠聊天记录回忆。

### 最小实现

新增文件：

```text
docs/optimization/failure_log.md
```

每条失败记录固定格式：

```text
## 问题标题

- 日期：YYYY-MM-DD
- 流程：新翻译 / QA / 公告 / 快速任务 / 部署
- 用户看到的现象：
- 实际根因：
- 影响范围：
- 修复方式：
- 回归验证：
- 是否已加入验证集：是/否
```

### 首批沉淀的问题类型

1. 上传失败只显示 Failed fetch。
2. 后端 traceback 暴露到前端。
3. 下载交付文件 Not Found。
4. 完整语言表误进项目术语库。
5. 术语导入提示成功但表格为空。
6. 公告任务完成后仍显示继续。
7. hard block 后没有修复入口。
8. 线上前后端版本不一致。
9. 删除项目失败。
10. 没配置 API 时仍允许启动 AI 流程。

### 验收

- 每个已修过的问题都能在失败库里查到。
- 每个高频失败至少绑定一个验证集 case。
- 新问题不允许只口头修，必须补记录。

## P2：自我沉淀进化

### 目标

做最简单的 SkillOpt-style 自我进化：不自动改代码，只自动/半自动沉淀“应该怎么改得更稳”。

### 最小实现

新增文件：

```text
docs/optimization/improvement_backlog.md
```

每条建议固定格式：

```text
## 改进建议标题

- 来源：哪个失败记录 / 哪个验证集 case
- 类型：流程 / UI / 错误提示 / 测试 / 文档 / 发布
- 建议内容：
- 预期收益：
- 风险：
- 验证方式：
- 状态：待评估 / 已采纳 / 已拒绝 / 已完成
```

### 进化规则

1. 验证集失败时，必须生成一条改进建议。
2. 同类失败出现 2 次，优先级自动升高。
3. 建议只能进入 backlog，不能直接改正式 prompt、harness 或代码。
4. 人工确认后，才进入开发计划。
5. 完成后必须补一个验证集 case 或更新旧 case。

### 这样做的价值

- 不需要 API。
- 不需要复杂平台。
- 不会自动污染生产规则。
- 能持续把真实问题转成项目资产。

## P3：发布前综合验收报告（暂不执行）

### 目标

每次准备发布或部署前，生成一份简单报告，明确这版能不能给组内使用。

### 最小实现

新增文件模板：

```text
docs/optimization/release_validation_report_template.md
```

报告字段：

```text
版本：
commit：
验证日期：
验证人：
验证范围：
通过 case：
失败 case：
阻断问题：
非阻断风险：
是否允许发布：是/否
```

### 发布前硬门槛

1. P0 验证集核心 case 全通过。
2. 没有交付文件 Not Found。
3. 没有前端 raw traceback。
4. 上传、下载、删除项目正常。
5. 线上 `/api/version` 与当前发布 commit 对得上。

## 执行顺序

### 第一步：先建验证集文档

交付：

```text
docs/optimization/validation_set/README.md
docs/optimization/validation_set/cases/*.md
```

只写文档，不写代码。

### 第二步：补失败轨迹库

交付：

```text
docs/optimization/failure_log.md
```

把最近已经出现过的问题先补进去。

### 第三步：补改进建议队列

交付：

```text
docs/optimization/improvement_backlog.md
```

把失败库里能转成行动的项全部转进去。

### 第四步：再考虑一键验证脚本（本轮不做）

最小脚本可以叫：

```text
scripts/run_manual_validation_index.py
```

第一版不需要自动操作浏览器，只做三件事：

1. 列出必须跑的 case。
2. 逐项提示验收标准。
3. 生成一份 release validation report 草稿。

后续再逐步把稳定 case 自动化。

## 不做事项

1. 暂不处理 API provider 能力。
2. 暂不做模型自动反思。
3. 暂不做自动改代码。
4. 暂不做复杂后台任务平台。
5. 暂不新建数据库表，先用 Markdown 文件跑通机制。

## 最小完成标准

这一轮完成后，项目里应该新增三类资产：

1. 验证集：知道每次要测什么。
2. 失败库：知道过去哪里坏过。
3. 改进队列：知道下一步为什么改。

只要这三类资产跑起来，后面才有资格谈更自动化的自我进化。
