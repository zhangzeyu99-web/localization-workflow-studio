# Localization Workflow Studio 项目优化计划：SkillOpt 思路落地版

## 结论

飞书文档里的 SkillOpt 思路值得用于本项目，但不能直接做“自动改代码”。更稳的落地方式是：把工作台真实任务、失败轨迹、用户验收标准和回归测试沉淀成可验证样本集；任何流程、提示词、harness、UI 文案和发布脚本的优化都先形成 proposal，再通过 held-out 验证门禁，最后人工确认进入正式版本。

当前项目已经有较好的基础：后端 workflow 已拆成模块、`main.py` 已瘦身、已有后端测试与 Playwright E2E、已有发布包脚本和部署检查。下一步重点不应是继续堆功能，而是让“用户真实跑不通的问题”可复现、可评分、可防回退。

## 十个可行优化项

| # | 优化项 | 为什么值得做 | 验收方式 |
|---|---|---|---|
| 1 | 建立真实任务回放集 | 当前问题多来自真实使用链路，单元测试覆盖不到用户困惑和流程断点 | 至少沉淀 30 个真实任务样本，覆盖新翻译、QA、公告、快速任务、部署 |
| 2 | 建立流程 verifier | 不能只看命令 exit code，要判断用户是否拿到可用结果 | 每条样本都有 PASS/FAIL 规则，例如“交付文件可下载”“hard block 不死路” |
| 3 | 建立失败轨迹库 | Failed fetch、Not Found、413、Internal Server Error 等反复出现，需要系统化归因 | 每类失败都有复现输入、用户可读错误、修复入口和回归用例 |
| 4 | 项目 prompt / harness 变更 proposal 化 | 自动改 prompt 或规则容易让项目质量漂移 | 变更先进入建议队列，展示差异、影响范围、验证结果，人工确认后生效 |
| 5 | 公告流程专项验证集 | 公告是多步骤、最容易卡住的流程，且依赖术语、译文反查、AI、QA 和交付 | 建立 8-10 个公告样本，覆盖 TXT/DOCX/XLSX、无术语、有 hard block、多语言 |
| 6 | 语言包术语提取专项验证 | 完整语言表误导入术语库、STEP4/5 分流、候选确认是高风险点 | 验证“完整语言表不能直入术语库”“候选确认后才入库”“目标语言自动识别” |
| 7 | Provider/API 稳定性样本集 | 工作台要脱离 Codex，只靠后端和 API provider 稳定运行 | 覆盖无 key、错误 key、429/5xx、长文本断点续跑、batch 失败修复 |
| 8 | 发布部署 skill 化 | 线上部署问题不是业务逻辑，而是包、环境变量、前端构建、data root、反代一致性 | 发布前必须通过 package check、deployment_check、stability_check 和下载验收 |
| 9 | UI/UX 观察清单 | 用户反复反馈“看不懂、按钮不知道干什么、结果去哪了” | 每个主页面有用户目标、主按钮、状态、失败恢复和交付入口评分 |
| 10 | 小步灰度优化机制 | SkillOpt 的关键不是多改，而是只接受验证变好的改动 | 每次优化只改一个主题，使用固定样本集对比，失败自动回滚或拒绝进入主线 |

## 分阶段执行计划

### 阶段 0：建立优化基线

目标：先冻结当前可用版本，避免优化过程中把已稳定功能改坏。

动作：

1. 记录当前 commit、版本号、发布包路径和本地/线上启动方式。
2. 固定基础验证命令：
   - `python -m pytest -q`
   - `python -m compileall -q backend workflow scripts`
   - `python -m ruff check backend/app backend/tests scripts --select E9,F`
   - `cd frontend && npm run build`
   - `cd frontend && npm run e2e -- --workers=1`
   - `python scripts/deployment_check.py --base-url <url>`
   - `python scripts/stability_check.py --base-url <url>`
3. 建立 `docs/optimization/` 目录，存放样本、评分规则、回放记录和优化 proposal。

验收：基线验证通过，且后续所有优化都能与该基线对比。

### 阶段 1：真实任务回放集

目标：把“用户实际会怎么用”变成可复现任务，而不是只靠开发者记忆。

首批样本建议：

1. 新翻译任务：空 EN 表翻译到交付。
2. 新翻译任务：已有译文直接 QA 到交付。
3. 新翻译任务：完整语言表进入 STEP4，STEP5 扫描术语候选。
4. 术语误导入拦截：完整语言表不能直接进入项目术语库。
5. 译文归档导入：多语言表导入 EN/KR/JP 并可导出。
6. 快速任务：上传 workbook 后直接翻译。
7. 快速任务：上传已有译文后直接校对。
8. 公告 TXT：术语提取、反查、AI 翻译、QA、交付。
9. 公告 DOCX：同格式交付。
10. hard block 场景：QA failed 后仍能看到问题、下载问题交付、修复后重新交付。
11. 上传超限或格式错误：用户看到人话提示，不展示 traceback。
12. 发布部署：Linux data root、API、静态前端、下载链路全通。

验收：每个样本都有输入文件、操作路径、预期结果、失败判定和清理方式。

### 阶段 2：流程 verifier

目标：把“看起来跑完了”升级为“用户拿到了可用产物”。

每类流程的最小 verifier：

- 新翻译任务：生成 final/changes，下载不为 404，归档计数正确。
- QA：failed 时必须显示问题原因和下一步；passed 时允许交付。
- 公告：最终 ZIP 只含成品和 QA 摘要；过程文件不混入最终交付。
- 术语：完整语言表只进候选，不直入项目术语库。
- 快速任务：中断后继续，不重复生成同一任务。
- 部署：`/api/version`、`/api/health`、上传自检、下载交付全通。

验收：每个 verifier 返回明确的 PASS/FAIL 和用户可读失败原因。

### 阶段 3：失败轨迹库与错误提示优化

目标：把过去反复出现的问题变成可搜索、可复现、可回归的资产。

优先收录失败类型：

1. `Failed to fetch`
2. `Internal Server Error`
3. 下载 `Not Found`
4. 上传 `413 Request Entity Too Large`
5. Python traceback 暴露到前端
6. provider 未配置仍启动 AI 任务
7. hard block 后无修复入口
8. 任务完成但状态仍显示继续
9. 术语导入成功提示但列表为空
10. 线上前后端版本不一致

验收：每类失败至少有一个回归测试或 smoke 场景，前端错误提示不暴露原始 traceback。

### 阶段 4：Prompt / Harness proposal 机制

目标：借鉴 SkillOpt，但保留人工控制，不让自动优化直接污染项目规则。

动作：

1. 项目提示词、项目 harness、持续改进建议统一进入“建议队列”。
2. 每条建议展示：来源任务、建议内容、影响范围、验证结果、是否已采纳。
3. 人工点击采纳后，才写入项目 profile/harness。
4. 每次采纳生成一次快照，允许回滚到上一版。

验收：翻译和 AI QA 使用的是已采纳版本；未采纳建议不影响正式任务。

### 阶段 5：公告和术语专项优化

目标：优先收束用户最容易卡住的两条复杂链路。

公告链路必须明确：

1. STEP1 只上传公告源文档。
2. STEP2 选择约束来源：项目 QA 归档默认参与，完整语言表可选上传。
3. STEP3 选择目标语言。
4. STEP4 从公告正文提取临时术语，不写回项目术语库。
5. STEP5 根据临时术语反查译文。
6. STEP6 生成翻译准备包。
7. STEP7 直接调用已配置 AI 翻译，外部 response 只是备用入口。
8. STEP8 QA 后显示问题和修复入口，hard block 不是死路。
9. STEP9 生成交付包后标记任务完成，并进入项目交付页。

术语链路必须明确：

1. 完整语言表不能直接导入项目术语库。
2. 完整语言表进入候选扫描。
3. AI 漏词补充默认开启，但只进入候选。
4. 人工确认后才进入项目术语库。

验收：公告和术语各有完整 E2E 样本，且状态、按钮、下载入口与用户预期一致。

### 阶段 6：发布部署 skill 化

目标：把“本地能跑”升级为“组内可用、数据不泄露、任务不断、错误能看懂、交付能下载”。

动作：

1. 发布包构建必须脱敏：不带 `.git`、`node_modules`、`.venv`、`lws-data`、SQLite、上传文件、API key。
2. 发布包必须带 `frontend/dist`，线上不依赖 Vite dev server。
3. Linux 启动脚本统一设置 `LWS_DEPLOYMENT_MODE`、`LWS_DATA_ROOT`、`LWS_CORS_ORIGINS`。
4. 部署后跑 `deployment_check.py --require-cloud --require-provider`。
5. 跑 `stability_check.py`，验证创建项目、上传、AI 分析、翻译、QA、公告和交付下载。
6. 建立回滚包和数据备份策略。

验收：线上用真实 URL 跑完整 smoke，交付文件可下载，测试项目可删除。

## 不建议现在做的事

1. 不建议直接让模型自动改生产代码并提交；风险高，验证成本大。
2. 不建议马上上多用户权限系统；当前更急的是单实例稳定和数据边界。
3. 不建议把所有失败日志喂给模型；里面可能包含用户文件名、文本和 API 相关信息。
4. 不建议大规模改 UI 视觉风格；应先修流程层级、状态、按钮和错误提示。
5. 不建议把 SkillOpt 当作“自动优化魔法”；它的核心价值是样本、评分、门控和小步验证。

## 下一步建议

第一步先做“真实任务回放集 + verifier”，因为这能直接解决现在最痛的问题：每次修一个点，另一个流程又坏。没有回放集，后续任何优化都会靠人工反复点页面，成本高且容易漏。

推荐本周最小交付：

1. 建立 `docs/optimization/task_replay_set.md`。
2. 整理 12 个首批任务样本。
3. 给 5 个最高风险样本写自动 verifier。
4. 把发布部署检查纳入同一套验收。
5. 之后再进入 prompt/harness proposal 和 SkillOpt-style 复盘。
