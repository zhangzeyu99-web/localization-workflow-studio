# 游戏台词翻译与校对要求

> 版本：2026-07-21
>
> 本版新增：对白语境分包、跨行续句检查、术语冲突分级、历史译文复审、机审误报裁决、二次纠偏输入完整性和高改动率复核门禁。

## 1. 适用范围

本规范适用于游戏对白、剧情文本、角色独白、战斗语音、NPC 对话、任务对话和带角色口吻的系统提示。它约束初译、既有译文校对、多语言回填和最终交付。

本规范补充以下通用流程，不替代它们：

- 术语一致性：`docs/TERMINOLOGY_TRANSLATION_PROOFREADING_STANDARD.md`
- 深度逐句校对：`docs/DEEP_LINE_PROOFREADING_SUBAGENT_WORKFLOW.md`
- 大文本多语言任务：`docs/LARGE_TEXT_MULTILINGUAL_WORKFLOW.md`
- 正式翻译证据和门禁顺序：`docs/QUALITY_GATES.md`

## 2. 核心原则

1. 准确传达说话意图、情绪和人物关系，不按中文词序机械直译。
2. 译文必须像目标语言角色会自然说出的话，而不是说明文或机翻腔。
3. 角色人设、称谓、礼貌等级、口头禅和同一剧情段内的句式保持一致。
4. 术语表、项目 brief、历史已验收交付和官方命名优先；术语命中是约束输入，不做脱离语境的机械替换。
5. 占位符、程序标签、富文本、数字、日期、单位、范围和换行结构不得被破坏。
6. 只处理用户指定语言和单元格；源文列、未请求语言列和保护列不得改写。
7. 除非用户明确要求，不使用 Google Translate、浏览器机翻或其他外部机翻做初译。

## 3. 标准执行流程

1. 每个新任务重新扫描用户指定目录、输入文件、当前术语表和项目资料，不继承上一任务的表结构或完成状态。
2. 确认目标语言、源文列、ID 列、保护列、是否原文件写回、改动标记方式和是否触发深度逐句校对。
3. 先按 `dialogue`、`narrative`、`ui`、`system` 分类，不得因为同在一个 workbook 就共用同一套风格提示。只有 `dialogue` 和带明确角色口吻的文本执行本规范的台词规则。
4. 读取项目 brief、角色设定、剧情上下文、最新术语表和历史已验收交付，形成当前任务约束快照；术语冲突必须在进入模型前单独标记。
5. 对历史译文、翻译记忆和空白占位标记做清洗。历史已验收译文可以复用，但仍须进入本次语义审校；`【无文本】`、`None`、`???` 等哨兵值不得当作正常台词直接继承。
6. 按语言独立翻译或校对；先保证语义和角色声音，再优化目标语言口语自然度。
7. 全量执行基础结构 QA；hard blocker 未归零时不得写回成品。
8. 用户明确要求逐句、逐行、深度或全量审校时，按完整对话轮次分包，执行 subagent 审校和主控二次纠偏，不得只给模型孤立单句。
9. 只写回指定目标单元格；既有译文校对时，只给实际修改的目标语言单元格标黄。
10. 从最终成品重新读回，核对内容、结构、改动标记和未请求列，再生成 QA 摘要并交付。

## 4. 翻译前必须确认的上下文

单句台词不能只凭字面处理。可获得时，至少向翻译或审校模型提供：

- `id`：稳定行 ID 或资源键。
- `source`：中文源文。
- `speaker`：说话角色、性别或身份；没有可靠证据时不得臆测。
- `addressee`：听话对象及双方关系。
- `scene`：剧情节点、战斗、任务、商店、教程等场景。
- `previous_line` / `next_line`：相邻台词或必要上下文。
- `emotion` / `intent`：情绪、言外之意和这句话要达成的效果。
- `character_voice`：年龄感、身份、教育程度、正式度、口头禅和禁用表达。
- `term_hits`：命中术语、官方译名和允许的语境变体。
- `placeholders` / `tags` / `newline_shape`：技术结构。
- `length_limit` / `voiceover_limit`：UI、字幕、配音或口型限制。
- `translation_memory`：同角色、同剧情段或同项目已验收译法。

缺少说话人、指代对象、性别、剧情因果或双关信息，且不同解释会实质改变译文时，应标记 `NEEDS_CONTEXT`，不得擅自补设定。

### 4.1 对白语境窗口

- 默认至少提供当前行前后各 1 条台词；存在指代、接句、打断、省略、问答、笑点回收或连续动作时，扩展到能还原完整语义的最小对话轮次。
- 相邻行共同组成一个句子时，翻译和 QA 必须按组合后的完整句子判断，再分别写回原行；不得把每行强行改成独立完整句。
- `previous_line` 或 `next_line` 缺失并不自动阻塞，但审校模型不得据此臆测说话人、关系、性别或剧情事实。
- workbook 没有 speaker 列时，可以使用资源 ID、连续行和项目资料推断语境边界；没有可靠证据时只记录 `speaker_unknown`，不编造角色身份。
- 同一中文源句出现在不同角色或不同剧情段时，不得仅按源文去重；去重键至少包含文本类型、说话人或场景语境。

## 5. 台词翻译规则

### 5.1 语义和信息

- 不漏掉否定、条件、转折、因果、时间、数量、程度和说话对象。
- 不增加源文没有的剧情事实、角色态度、性别、亲疏关系或世界观设定。
- 中文省略主语或宾语时，按上下文补足目标语言语法；证据不足时改用中性表达或请求上下文。
- 同一段对话中的代词、指代、时态和事件顺序必须连贯。

### 5.2 角色声音和关系

- 同一角色的正式度、语速感、词汇难度、攻击性和幽默感保持稳定。
- 敬语、第二人称、头衔、昵称和亲昵称呼应反映角色关系，不可只按字面统一。
- 角色成长或关系变化导致口吻变化时，以剧情节点为准，不强行全局统一。
- 粗口、俚语和讽刺应保留功能与强度，并符合目标市场分级；不得无故弱化或升级。

### 5.3 口语自然度

- 优先使用目标语言常见口语搭配、语序和省略方式，避免逐词对应和中文式连接词。
- 短句保持利落；情绪爆发、迟疑、打断和停顿可按目标语言习惯重组标点，但不能改变剧情信息。
- 不为显得“文艺”而拔高普通角色，也不把庄重角色改成随意口吻。
- 错误提示、教程和系统播报不是角色台词时，优先清晰、简洁和可操作性，不套用戏剧化表达。

### 5.4 笑点、双关和文化适配

- 无法直译时优先保留笑点、讽刺、威胁、安慰等交际效果，而非字面结构。
- 改写不得破坏后续剧情回收、任务谜题、角色名梗或画面信息。
- 文化替换必须符合项目风格和目标市场；高风险双关应在 QA 备注中说明处理理由。

### 5.5 术语、名称和一致性

- 进入翻译前，将命中项分为 `hard_term`、`soft_term` 和 `term_conflict`：
  - `hard_term`：已确认的人名、地名、阵营、活动、道具、技能和系统专名，必须保持官方写法。
  - `soft_term`：普通名词、动作、称谓和可按语境变形的短语，只作为参考，不要求逐字命中。
  - `term_conflict`：术语表、项目 brief 或历史交付存在多个互斥写法，必须先裁决或标记待确认，禁止把多个候选同时作为硬约束传给模型。
- 正文允许因语法产生自然的词形、冠词、单复数、格和大小写变化，但不得更换已确认专名、扩大或缩小术语含义。
- 同一中文词兼有普通词和系统名用法时，必须结合上下文判断，禁止把普通词误改成系统名。
- 亲属称谓、职业和头衔不因术语表首字母大写就一律大写。例如英文中的 `Grandma` 可作名字使用，`my grandma` 则可按普通亲属称谓小写；`agent`、`talent scout`、`mayor` 是否大写取决于句法和是否作为正式称号。
- 人名拼写冲突不得靠字符串替换解决。优先级为：项目方确认或官方资料 > 当前项目 brief 中确认的人物表 > 已上线且上下文一致的多数用法 > 最新术语表单条记录。仍无法裁决时返回 `TERM_CONFLICT`。
- 相邻台词、同角色台词和同一剧情段应检查称谓、关键词和固定句式的一致性，但不得为了表面一致牺牲自然口语。

### 5.6 长度、字幕和配音

- 有字符数、字幕行数、显示宽度、语音时长或口型限制时，以项目硬限制为准。
- 缩短时先删除目标语言中的冗余，不删除剧情信息、动作指令、否定、数量和术语。
- 没有明确长度限制时，不为追求与中文等长而牺牲自然度。
- 配音台词需要额外检查可说性、呼吸点、重音和时长；仅凭文本无法判断时标记为配音复核项。

### 5.7 跨行续句、打断和标点

- 当前行以小写字母开头不自动算错。若上一行以未完成从句、省略号、冒号或打断标记结束，当前行可能是合法续句，必须成对审校。
- 当前行以连词开头也不自动算错；先判断它是独立口语句、承接上一行，还是被错误拆行。
- 打断、停顿、犹豫和话题转折按目标语言规范统一。英文项目默认优先使用 `U+2014 em dash` 表示打断或插入，不在同一批次混用双连字符、普通连字符和 em dash；项目已有明确标点规范时以项目规范为准。
- 引号、句号、问号和省略号按目标语言标点规则判断。机审不得仅因为中文引号与英文引号位置不同就判定损坏。
- 相邻两行组成一句话时，分别写回后仍要能自然连读；不得为消除“句首小写”告警而破坏连贯性。

### 5.8 历史译文和翻译记忆

- 历史已验收译文是高优先级证据，不是不可修改的真值；本次上下文、角色关系或术语裁决发生变化时仍需重新判断。
- 历史译文复用行必须和新增初译行一起进入逐行审校，QA 摘要分别记录复用量和复用后修改量。
- 同一源文在 UI、系统提示和角色对白中可能需要不同译法；翻译记忆键必须包含文本类型或语境，不能只用中文源文全局复用。
- `【无文本】`、`None`、`N/A`、`???`、占位 ID 等哨兵值应按项目配置映射、保留或置空，不得被误当成正常中文残留或直接继承到目标语言。

## 6. 技术与格式保护

- 占位符、变量、程序 token、HTML、BBCode、颜色标签及其顺序必须保持。
- 数字、日期、时间、百分比、货币、单位、上下限和范围必须完整；可按目标语言格式本地化，但不得改值。
- 区分真实换行和字面 `\n`；未经要求不得增删换行。
- `|` 等运行时分隔符必须保留数量和顺序，同时检查分隔符两侧的目标语言空格；“结构未丢失”不等于最终拼接后可读。
- 保留资源 ID、键名和公式；不得把翻译写入源文列或其他语言列。
- 目标语言允许正常的变音符号和本地标点；只拦截不属于该语言的乱码、异常全角字符、U+FFFD 和连续问号乱码。

## 7. 既有译文校对与改动标记

校对不是重译整表。现有译文准确自然时保留，只修改有明确语义、术语、角色声音、语法或母语自然度收益的位置。

Excel / 飞书表格的改动标记规则：

- 只给实际修改的目标语言单元格标黄。
- 中文源文、ID、未请求语言、未修改译文均不标黄。
- 不按整行或整列标黄；一个单元格未改，就保持原样。
- 多语言完成状态可在对应语言的状态单元格打勾，但不得因此标黄整列。
- 最终读回必须满足：`实际修改单元格集合 == 黄底单元格集合`。

## 8. QA 分层

### 8.1 基础结构 QA：每次全量执行

- 文件、工作表、行、ID 和目标列完整。
- 源行与目标译文一一对齐，无空译文、重复 ID、漏行或串行。
- 占位符、标签、换行、数字、日期、单位和范围无漂移。
- 目标文本无中文残留、乱码或不属于该语言的异常字符。
- 源文列、保护列和未请求语言列零改动。
- 最终文件重新读回，hard blocker 为 0。

### 8.2 台词语义 QA：翻译或“校对”任务必须执行

逐条检查：

- 漏译、误译、反义、主客体错误和指代错误。
- 角色人设、关系称谓、敬语等级和语气漂移。
- 情绪、潜台词、笑点、讽刺和剧情因果是否保留。
- 术语、名称、代词、时态和相邻台词是否一致。
- 目标语言是否自然、可说、符合 UI 或字幕场景。

只有结构 QA 和台词语义 QA 都完成，才能称为“已校对”。

### 8.3 深度逐句校对：按用户触发

用户明确要求“逐句、逐行、深度、完整、全量审校或 LQA 深校”时，按 `docs/DEEP_LINE_PROOFREADING_SUBAGENT_WORKFLOW.md` 执行：

- subagent 只输出 `keep`、`change` 或 `flag` 建议，不直接修改成品。
- 审校输入除源文和当前译文外，至少包含文本类型、相邻台词、历史来源、术语分级和技术 token；缺少会改变判断的上下文时必须 `flag`，不得猜测。
- `change` 必须给出明确错误类型、证据和可验证收益。只写“更自然”“更流畅”而没有指出当前译文问题的建议，默认不接受。
- 主控对建议做二次纠偏，回退语义变窄、过度术语化、人物口吻漂移、擅加称谓、无依据增强情绪和纯风格折腾。
- 接受修改后重新跑结构 QA、改动标记检查和最终读回。

### 8.4 机审告警分级与人工裁决

机审结果必须分层，不能把所有规则命中都算 hard blocker：

- `deterministic_hard`：空译文、错位、占位符或标签损坏、数字变值、乱码、未请求列改动、最终读回不一致。命中即阻塞。
- `semantic_hard`：关键剧情误译、反义、主客体或指代错误、已确认官方名称错误。必须由模型或人工复核并修正后清零。
- `context_review`：句首小写、标题式大小写、亲属称谓大小写、职业称谓、人名近似命中、引号标点、长度软提示和术语部分命中。必须结合文本类型和相邻台词裁决，不得自动替换。
- `style_watch`：口语节奏、轻微冗长、同义词选择和标点偏好。只有当前译文明显不自然或违反项目风格时才修改。

以下情况不能单凭规则命中判错：

- 上一行未完结时，当前行以小写或连词开头。
- 亲属称谓或职业词在普通句法位置小写。
- 英文引号、句号和问号位置与中文不同，但符合英文标点规范。
- 短 UI 标签使用项目约定的 Title Case。
- 对白中的普通词没有逐字命中术语表，但语义正确自然。

每个被保留的 `context_review` 告警都要在 QA 摘要中记录数量和裁决理由；“规则有误报”不能只写在口头说明里。

### 8.5 二次纠偏输入完整性和独立性

- 纠偏审计必须同时看到 `source`、`current_translation`、`suggested_translation`、`previous_line`、`next_line`、`speaker/scene`、`term_policy`、`review_reason` 和技术 token。只把建议译文和理由交给审计模型，不能构成有效纠偏。
- 审计输出至少包含 `ACCEPT`、`REVISE`、`REVERT`、最终译文和具体依据；`REVERT` 必须能恢复当前译文，不能依赖审计模型凭空重建。
- reviewer 和 auditor 应使用不同提示、独立 checkpoint 标识，并避免共享“默认接受修改”的措辞。
- 审计优先保护语义、人物关系和上下文连贯性；纯风格建议的默认决策是 `REVERT`，除非当前译文明显不自然或违背角色声音。

默认触发额外校准抽查的信号：

- 500 行以上对白包的建议修改率超过 35%。
- 100 条以上修改建议的审计接受率超过 98%。
- 全量对白审计没有任何 `REVERT`，但存在大量纯自然度或风格改写。
- 历史译文占比较高，却出现接近重译整表的修改量。

触发任一信号时，主控应对修改建议再独立抽查至少 50 条或 10%，取较大者；按错误类型、历史来源和角色分层抽样。抽查未通过前不得把高接受率当作高质量证据。

## 9. Hard blocker

出现以下任一问题不得交付：

- 漏行、错列、错位、空译文或重复 ID。
- 占位符、标签、数字、日期、单位、范围或换行损坏。
- 关键剧情信息漏译、反义、人物关系或指代错误。
- 强术语、人名或官方名称错误。
- 新增正式人名或专名存在未裁决的 `TERM_CONFLICT`，但成品已擅自固定其中一个写法。
- 未请求语言列、源文列或保护列被改写。
- 中文残留、乱码或不可读文本。
- 黄底包含未修改单元格，或实际修改单元格未标黄。
- 最终成品未完成真实读回验证。

`context_review` 或 `style_watch` 告警本身不是 hard blocker；未经过上下文裁决就批量自动修正，才构成流程失败。

## 10. 交付与 QA 摘要

最终交付目录只保留成品和 QA 摘要，不混入 workpack、response、JSONL、日志或缓存。

QA 摘要至少记录：

- 输入文件、目标语言和处理行数。
- 结构 QA 是否通过及 hard blocker 数。
- 台词语义 QA 的审校行数和最终修改数。
- 唯一对白语境数、历史译文复用数和复用后修改数。
- 术语命中行数，以及 `hard_term`、`soft_term`、`term_conflict` 的数量和裁决结果。
- 逐句审校建议数、建议修改率、接受数、重写数、回退数和审计接受率。
- 机审各类告警数、实际修正数、误报保留数和裁决理由。
- 主控在模型审校后追加的最终修正数，例如术语、拼接空格、标点统一和哨兵值修正。
- 各语言修改数。
- 实际修改单元格数、黄底单元格数、中文列黄底数和未请求语言改动数。
- 是否启用深度逐句校对。
- 是否使用外部机翻。
- 最终文件路径和读回差异数。

## 11. 最终验收标准

满足以下条件才可声明完成：

1. 指定语言全部处理完成，源行对齐且目标列无空白。
2. 台词在目标语言中准确、自然，人物声音和上下文一致。
3. 跨行续句、打断、引号和对话轮次已经按相邻上下文检查。
4. 术语、占位符、标签、数字、单位、运行时分隔符和换行全部通过。
5. `TERM_CONFLICT` 已裁决或明确阻塞，机审上下文告警已逐类判定。
6. 未请求语言、中文源文和保护列零改动。
7. `hard blocker = 0`。
8. `实际修改单元格数 = 黄底单元格数`，且中文列黄底数为 0。
9. 最终成品读回差异为 0。

## 12. 典型判定示例

| 场景 | 错误做法 | 正确判定 |
| --- | --- | --- |
| 人名存在 `Rafeal / Rafael` 两种写法 | 仅按术语表第一条批量替换 | 标记 `TERM_CONFLICT`，依据官方资料或项目方裁决；对白自然度规则不能掩盖专名冲突 |
| `my grandma` 被机审提示未命中 `Grandma` | 自动改成大写 | 先判断是名字还是普通亲属称谓；普通句法位置小写可以正确 |
| 上一行以未完成从句结束，下一行以小写开头 | 把下一行强制改成独立大写句 | 将两行连读后判断，保留合法续句 |
| 中文使用引号，英文句号位于引号内 | 判定标点损坏并机械移位 | 按目标语言标点规范裁决，不比较中英文标点位置是否逐字相同 |
| 英文对白中混用双连字符和打断标点 | 只检查字符可读，不统一 | 按项目规范统一；无项目规范时英文默认使用 `U+2014 em dash` |
| 系统文本含 `|` 分隔符 | 只检查数量相同 | 同时检查顺序和分隔符两侧空格，验证运行时拼接后的完整句子 |
| 源文为 `【无文本】`、`None` 或 `???` | 直接复制到目标语言 | 识别为哨兵值，按项目配置映射、保留或置空，并在 QA 中单列 |
| 独立 UI 资源名命中强术语 | 因“台词不用苛求术语”而自由改写 | 先确认文本类型；非对白的独立资源名仍按 `hard_term` 执行 |
